AI 代理真正的風險，不是它偶爾答錯，而是公司竟然讓一個會答錯的系統拿著正式環境的永久通行證。

現在市場最愛談的是模型又變聰明多少：推理測驗多幾分、上下文多幾十萬 token、寫程式成功率再提高幾個百分點。但企業真正該問的問題是：它判斷錯的那一次，究竟能做什麼？

假設代理執行動作的正確率高達 99.5%，每做 1,000 次決策仍有 5 次可能出錯。若它只能整理會議摘要，代價可能是一段需要重寫的文字；若它同時握有 GitHub 寫入權限、Stripe 金鑰、Slack 管理權和正式資料庫帳密，那 5 次就是 5 張資安事故彩券。

過去聊天機器人亂講話，最多讓品牌公關連夜滅火。現在的代理可以直接改程式碼、寄信給客戶、刪除資料、核准退款，甚至把錯誤部署到正式環境。模型能力只是引擎，權限設計才是煞車；偏偏多數團隊忙著換更大的引擎，煞車仍沿用十年前自動化腳本的做法。

最常見的配置很簡單：把 `GITHUB_TOKEN`、`DATABASE_URL` 或支付金鑰塞進環境變數，再用 system prompt 告訴代理「只能修改測試資料」「不得刪除正式紀錄」。問題是，prompt 是文字，不是安全邊界。只要惡意網頁、被污染的文件或工具回傳內容成功誘導模型一次，攻擊者就可能借代理之手使用整組權限。

更合理的設計，是讓代理只有「提案權」，沒有長期「執行權」。

例如代理想替 GitHub issue 1842 加上 `bug` 標籤，它先送出包含動作、目標與理由的請求。位於代理程序之外的權限服務確認規則後，才簽發一張只能使用一次、幾分鐘內到期，而且只能執行該動作的憑證。代理不接觸真正的上游金鑰；即使它被 prompt injection 控制，攻擊者拿到的也不是整間公司的萬用鑰匙。

GitHub 在 2026 年 10 月 28 日正式推出 Agentic Workflows，算是把這套概念做成了可觀察的產品。這項功能在同年 6 月進入公開預覽，代理預設只有唯讀權限，並在沙箱容器內運作。它提出的修改要先通過威脅偵測，再由另一個持有寫入 token 的 job 套用；企業還可以透過 GitHub Environment，要求真人審核後才放行。

這個切割比模型在程式測驗上再多拿三分更重要。它把「代理被騙」與「正式環境真的遭修改」拆成兩件事，中間多出一道可以拒絕、記錄與追責的關卡。

但別因為看到「沙箱」兩個字就放心。GitHub 自己的 FAQ 已說明，若工作流程作者直接開放寫入權限，或加入自訂 job，原本的保護不會自動延伸。採用 Actions Runner Controller 的自架環境，還可能透過具特權模式的 Docker-in-Docker sidecar 啟動容器。表面上代理被限制得很嚴，隔壁卻坐著一個高權限元件；真正的攻擊面從來不是產品架構圖上那個漂亮的盾牌，而是整條執行路徑。

GitHub 也替失控成本設下具體上限。每個 AI Credit 定價 0.01 美元，每次執行預設最多 1,000 點，也就是 10 美元；企業預設每日上限為 5,000 點，單次威脅偵測最多 400 點，代理步驟則限制在 20 分鐘。這些看似財務設定，其實也是資安設定：一個可以無限重試、無限呼叫工具的失控代理，本質上就是由受害公司付帳的自動化攻擊程式。

Accenture 在 GitHub 公告中宣稱，一位主管每週因此省下約 29 小時，卻沒有公開測量方式。這正是目前代理市場的典型話術：效益用一個漂亮數字帶過，風險則藏在數十頁設定文件裡。企業採購順序應該倒過來——先看權限圖、失敗率、阻擋紀錄與復原流程，再看那張「每週省下幾小時」的簡報。

Grok Build 的資料外洩則證明，風險不一定來自什麼高深的模型攻擊。Claroc 發現，Grok Build 建立的分享連結把四個隨機單字放在子網域位置，雖然號稱最高約有 38 bits 的熵，連結卻會被 passive DNS 系統記錄，最後進入可公開搜尋的資料庫。使用者以為「沒把連結給別人就安全」，網路基礎設施卻早已替它留下足跡。

曝光的 SpaceXSI 資料包括涵蓋 594 個策略客戶的業務版圖、8 份 X 廣告提案、4 個仍在使用的廣告客戶看板，以及 2 份 X 品牌安全手冊。被發現的頁面中只有一個要求密碼。Claroc 還辨識出 6 家《Fortune》500 大企業，以及 26 家員工超過 1,000 人的組織；研究團隊估計，約 2% 的曝光內容達到最高等級的風險範圍。

這不是模型突然產生邪惡意識，而是一個分享網址設計錯誤。真正值得怕的是放大效應：AI 讓每個部門都能快速生出內部工具、資料看板與臨時應用，但資安團隊的人數沒有跟著增加十倍。過去一年做 20 個系統，還能逐一檢查；未來一年由代理做出 2,000 個小工具，任何不安全的預設都會被複製 2,000 次。

購物場景也已經出現同一種落差。品牌保護公司 Podqi 針對 151 個品牌，測試 Gemini、ChatGPT 與 Perplexity 共 6,795 次回答。Perplexity 有 15% 的回答出現仿冒、失效或被重新註冊的危險網站；ChatGPT 為 8%，Gemini 為 4%。ChatGPT 即使碰到這類網址，也只有 24% 的情況會主動警告使用者。

這份研究當然有侷限：提示詞由 Podqi 自行設計，受測品牌 Madhappy 又是它的客戶。但即使採用表現最好的 Gemini，4% 仍等於每 25 組回答就有一組出現風險網址。當 AI 只提供資訊時，使用者還有機會察覺；一旦代理能自動下單、填信用卡資料，4% 就不是「偶爾引用錯誤」，而是可規模化的釣魚、假貨與盜刷入口。

更少人談到的是：AI 代理正在把原本分開的供應鏈，壓縮成一條使用者完全看不見的信任鏈。

使用者以為自己只在和 Notion AI 對話，資料實際上可能經過 Notion、模型基礎設施供應商、雲端平台、紀錄系統與儲存服務。2026 年 11 月，Notion 表示 Fireworks AI 遭入侵的事件影響約 1% 的自家客戶。攻擊者取得部分 Notion AI Insights 對話紀錄，其中包含使用者送進模型的文字與模型輸出。Fireworks 表示，攻擊者先突破其雲端供應商，再進入開發系統；這已是 Fireworks 兩個月內第二起公開事件。

台灣企業尤其容易低估這一層。導入 SaaS 時，採購與資安部門可能審查主要品牌，卻未必知道它背後還串了哪一家模型託管商、向量資料庫或觀測平台。醫院、金融機構與電子製造商若把內部知識庫接上代理，資料邊界就不再只是「有沒有送到國外」，而是「沿途有幾家公司能碰到提示詞、回覆、附件和操作紀錄」。

反方會說，若每個動作都要真人按同意，代理還有什麼意義？這個批評在低風險工作上完全成立。讀取公開 issue、整理文件、產生草稿、執行測試，以及在可隨時丟棄的環境修改程式，都不該卡著主管簽核。

但權限應按後果分級，而不是把「全自動」當成高級方案販售。查詢庫存和刪除客戶資料，不是同一條便利性滑桿上的兩個刻度。低風險、可逆的動作可以自動執行；範圍明確的修改交給政策引擎驗證；涉及付款、對外發布、正式部署與不可逆刪除，就必須使用一次性授權，必要時再加真人批准。

最後勝出的代理平台，不會是「什麼都敢替你做」的那一家，而是能清楚證明：這次動作為何被允許、憑證能做什麼、資料經過哪些供應商，以及其他防線全部失效時，損害會在哪裡被截斷。

### 值得關注

2027 年中以前，一次性能力憑證與權限有效時間，會像過去的靜態加密一樣，從工程細節變成企業採購表上的標準欄位。仍要求客戶把組織級永久 API key 直接貼進代理環境的廠商，會開始被視為不負責任。

GitHub 的「唯讀代理提出修改、另一個 job 負責寫入」模式也會走出軟體開發。客服代理可以提出退款，但真正扣款由獨立服務執行；人資代理可以草擬權限異動，但只有外部授權服務能簽發限定帳號、限定動作的短效憑證。

企業評測也會從「答案對不對」轉向「被攻擊時會做什麼」。採購方將要求測試 prompt injection、惡意工具回傳、重試風暴、供應商失陷與繞過審核等情境，並索取被阻擋動作比例、最壞損害範圍與平均撤銷時間。只有 benchmark，沒有行為測試的代理，進不了高權限正式環境。

最後，2027 年至少會有一起大型事故被媒體稱為「AI 代理失控」，事後卻發現根因毫不科幻：一把權限過大的長效 token、一個可被搜尋的分享連結、一個未審查的 connector，或供應商的開發環境遭入侵。這不代表代理是無辜的，反而會讓問題更清楚——智慧從來不是安全邊界，權限才是。
